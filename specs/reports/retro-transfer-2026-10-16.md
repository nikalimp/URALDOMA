# Ретро переноса uraldoma.ru — правки в методологию /site

Дата: 2026-10-16. Основа: скиллы `site` / `transfer-site` / `new-site`, флоу, стандарт, шаблоны, `specs/*` проекта, git-лог (14 коммитов за 15.10), история сессии.

Факты, от которых отталкиваюсь:
- Весь путь «анализ → spec → дизайн → сборка → прод» занят один день. Узкое место — не сборка, а факты клиента, доступы и хостинг.
- Дизайн менялся 5 раз уже на собранном сайте (тёплый дом → швейцарская типографика → светлая классика + тёмная тема → фуллскрин по направляющим → «Журнал» → дизайн-система + лого).
- Прод выложен без этапов 7–8: `06-launch-checklist.md` не тронут, Главред и Lighthouse не запускались, spec клиентом не утверждена, `specs/reports/` пуст (geo-check «до» не снят).
- Деплой: цикл редиректов на REG.RU, затем порт 22 закрыт для зарубежных IP — выкладка по push стоит, сайт обновляется zip-архивом руками.
- Контент-завод по-прежнему публикует в Tilda Feeds, хотя домен уже на новом сайте (риск №1 из аудита так и не закрыт задачей).
- Карточка в NikitOS: «Этап: 7. Сборка» при живом сайте; 04-plan описывает staging, который удалён.

Легенда: ★ — главное. «Куда» — какой документ править.

## A. Старт и среда
1. ★ **`/site` не был доступен как команда** — агент читал SKILL.md руками. Куда: `site/SKILL.md` + гайд. Правка: первая строка скилла — «если NikitOS не подключён к сессии, попроси подключить и остановись»; скиллы сайта зарегистрировать как скиллы аккаунта (propose_skills), чтобы `/site` работал в любой сессии.
2. **Папка проекта ≠ корень репозитория.** Шаблон считает `~/Desktop/<Клиент>/` репозиторием, а в УралДома там уже лежали `Content/`, `Objects/`, `Team/` → код ушёл в `site/`. Куда: `new-site` «Где что лежит». Правка: закрепить структуру `~/Desktop/<Клиент>/{site, Content, materials, media}`; репозиторий — всегда `site/`.
3. ★ **Синхронизация облако ↔ Mac через tgz и git bundle (резали по 3 МБ)** — потеря времени и ложные «неотправленные коммиты». Куда: гайд стартера «Сборка из Cowork». Правка: единственный источник правды — GitHub. Облачная сессия клонирует с GitHub и пушит ветки; Mac делает `git pull`. Файлы через мост Cowork не гоняем.
4. **Запрет удаления в Cowork** больше не блокер: есть запрос разрешения на удаление (`device_request_delete_permission`). Куда: гайд «Сборка из Cowork». Правка: «сначала запроси разрешение на удаление в папке проекта один раз — дальше `npm run check` на Mac через device_bash»; облачная сборка — запасной путь.
5. **Пуш в `main` из облачной сессии блокируется как production deploy, разрешение в чате не помогает.** Куда: `new-site` «Правила», гайд. Правка: стандартный контур — агент работает в ветках и открывает PR; Ник мержит (одна кнопка) либо просит фразой «смёрджи PR #N». Не обещать «буду пушить сам».

## B. Этап 1 — анализ сайта
6. ★ **geo-check «до» не снят, `specs/reports/` пуст** — отчёт «до/после» (этап 10) невозможен. Куда: `transfer-site` этап 1, `scripts/check.mjs`. Правка: geo-check запускается через device_bash на Mac (у него есть доступ к сайту), а не «Нику в терминале»; `check.mjs` сам пишет отчёт в `specs/reports/<дата>.md`; деплой на прод запрещён, пока нет `geo-check-before-*.md`.
7. ★ **Доступы к Метрике/Вебмастеру так и не получены** — базовая линия заявок и позиций отсутствует, spec §2 с TODO. Куда: `transfer-site` «Старт проекта». Правка: запрос доступов — задача дня 0 с дедлайном; без них вариант C не предлагать клиенту (нечем мерить «не хуже, чем до»). Минимум: экспорт Метрики за 12 мес и запросов Вебмастера в `specs/reports/baseline/` до смены DNS.
8. **Инвентаризация только текста.** Видео первого экрана (T19), 4 статьи из Tilda Feeds (T14), фото — не сняты на этапе 1. Куда: шаблон `00-transfer-audit.md`. Правка: раздел «Медиа и файлы»: видео, фото, PDF, шрифты, фавикон, OG — скачать в `materials/source-media/` сразу, пока есть доступ к CMS.
9. **Tilda — типовой источник.** Инвентаризация, интеграции форм, head-код, Feeds снимались через Tilda MCP вручную. Куда: `transfer-site` + скрипт в стартере. Правка: чеклист/скрипт «снять проект с Tilda»: страницы → `specs/source/`, Feeds (все посты, включая портфолио) → md, интеграции форм, head/CSS, sitemap, список получателей заявок.
10. **Соответствие `/tpost/*` → объект осталось `[?]` (T20a).** Куда: шаблон аудита §9. Правка: карта редиректов для постов портфолио строится на этапе 1 по заголовкам постов (там есть ЖК), а не откладывается.

## C. Этапы 2–4 — предложения и spec
11. **Spec не утверждена клиентом, но сайт на проде.** Флоу требует «письменное подтверждение» — в реальности решения принимал Ник. Куда: флоу + `new-site` «Этапы». Правка: ввести явный режим «ускоренный проект» (Ник = заказчик, у сайта нет пользователей): какие утверждения сворачиваются, какие нет (редиректы, право, базовая линия — нет). Режим фиксируется в шапке spec, а не возникает по ходу.
12. **Правило «факты только от клиента» vs «рыночные цены там, где нет цены клиента».** Куда: стандарт §7 / `new-site` «Правила». Правка: формализовать запасной путь: рыночный ориентир допустим с пометкой в контенте (`estimate: true`) и строкой в «Вопросы»; `check` показывает список таких мест; серийные страницы без фактов — noindex и вне sitemap (как сделали с кейсами) — записать как правило.
13. **Рекомендация Must №7 «переключить контент-завод» не стала задачей.** Куда: шаблон `05-tasks.md`. Правка: для ветки переноса шаблон задач содержит обязательный блок «Переезд»: карта редиректов, обход старых URL, переключение контент-завода, перенос счётчика Метрики, тестовые заявки, DNS, Tilda живёт 30 дней, мониторинг. Must из `01-transfer-proposals` → задачи автоматически.
14. **Хостинг в spec — `TODO(Ник): выбрать`.** Выбор REG.RU сделан позже и стоил двух сбоев. Куда: `02-spec.md` §7/§1, стандарт §1. Правка: хостинг и способ выкладки — обязательное поле spec до этапа 5; по умолчанию — проверенный хостинг из списка (см. H).
15. **Дата правок в журнале spec не по порядку (v0.3 выше v0.2)** — мелочь, но журнал читает клиент. Куда: шаблон spec: «новые строки — снизу».

## D. Дизайн
16. ★ **5 редизайнов после сборки.** Этап 4 прошёл формально (2 направления → A), а реальные предпочтения всплывали по одному. Куда: `03-design.md` шаблон, флоу этап 4. Правка: (а) до кода — 2–3 быстрых HTML/Claude Design прототипа главной в разных стилях, с референсами из Behance/Tilda-шаблонов — разбор референсов делаем на этапе 4, а не 6; (б) «заморозка дизайна»: после T03 любое изменение стиля = новая версия §N в 03-design + оценка в задачах (это уже делали — закрепить как правило).
17. ★ **Вкусы Ника переоткрываются в каждом проекте.** Куда: новый файл NikitOS `Resources/Frameworks/Дизайн — предпочтения Ника.md`, на него ссылается `03-design`. Содержание из этого проекта: швейцарская сетка 12 колонок, gutter 20 px, направляющие, H1 капсом, тёмная тема с переключателем (по умолчанию системная), «журнал»: фото > текст, курсив с засечками для акцентов, элементы 21st.dev без внешних библиотек, pill-кнопки, нумерация 01–04, фуллскрин-портфолио.
18. ★ **Дизайн-система как источник правды появилась в конце.** Куда: шаблон `03-design.md` → `03-design-system.md` + `design-system/tokens.json` в стартере. Правка: токены (цвет OKLCH, шрифты, сетка, радиус, движение), логотипы (полный/короткий SVG), компоненты; стили генерируются из tokens.json перед сборкой; сборка падает при цвете в обход токенов (уже реализовано — перенести в стартер).
19. **Логотип.** Исходники SVG появились на второй день, фавикона на сайте не было. Куда: `00-brief.md` часть A. Правка: «логотип в векторе (полный и короткий), фавикон, OG» — вопрос №1 брифа с пометкой «блокирует этап 4».
20. **Ошибки тёмной темы и сетки нашлись только авто-сравнением скриншотов (Playwright, 44 страницы).** Куда: стартер `scripts/`, `06-launch-checklist.md` §3. Правка: скрипт `theme-check` (каждый элемент меняет цвет в обеих темах, контраст) и `grid-check` (края блоков на направляющих) — часть `npm run check`, если тёмная тема включена.

## E. Фото и медиа
21. ★ **80 фото клиента обработаны ad hoc** (вертикали, шум, тон, webp 1440/720/wide, подписи-alt в `photos.ts`). Куда: стартер `scripts/photos.mjs` + соглашение `src/content/photos.ts`, стандарт §6. Правка: стандартный конвейер фото: входная папка → выравнивание, шум, webp в 3 размерах → подписи (alt) по правилу «только то, что видно». Бриф запрашивает папку фото на день 0.
22. **Видео первого экрана** до сих пор не перенесено (T19). Куда: стандарт §6 — лимит ≤ 3 МБ, постер, `<picture>`-fallback; в аудит — п. 8.

## F. Сборка и качество
23. **Главред и Lighthouse ни разу не запускались**, хотя стоят в задачах и критериях приёмки. Куда: `scripts/check.mjs`, GitHub Actions. Правка: Главред (`glavred.mjs`) и Lighthouse CI — внутри `npm run check` с порогами из стандарта; то, что не автоматизировано, не считается проверкой.
24. **04-plan устарел в тот же день** (описывает dev-поддомен, который удалили). Куда: `new-site` «Правила». Правка: решение, меняющее инфраструктуру или объём, правится в spec/plan тем же коммитом (правило «spec описывает реальный сайт» — есть во флоу, нет в правилах агента по сборке).
25. **Карточка клиента отстаёт от реальности** («Этап: 7. Сборка» при живом сайте). Куда: `new-site` «Этапы». Правка: строка «Этап» в карточке обновляется в конце каждого ответа, где этап сменился; `/site статус` сверяет карточку с `05-tasks` и spec и сообщает расхождение.

## G. Хостинг и запуск
26. ★ **REG.RU: цикл редиректов** (TLS завершает nginx, `%{HTTPS}` всегда off) **и закрытый порт 22 для зарубежных IP** — деплой из GitHub Actions невозможен. Куда: гайд стартера, новый раздел «Хостинги: что проверено». Правка: таблица хостингов с известными особенностями; REG.RU виртуальный — «SSH-деплой из GitHub не работает, https-редирект только через ISPmanager»; рекомендуемый по умолчанию — тот, где SSH из Actions проверен (Timeweb/Beget — проверить на следующем проекте).
27. ★ **Pre-flight хостинга до сборки пайплайна.** Куда: шаблон `05-tasks.md` блок «Запуск», `06-launch-checklist.md` §6. Правка: задача «проверить хостинг»: `nc` на 22 из GitHub (черновой workflow), поведение https-редиректа, права на `.htaccess`, лимит PHP для `lead.php`. Пока не зелёная — секреты не заводим.
28. **Ошибка ssh-keyscan была скрыта `2>/dev/null`** — в логе только «exit code 1». Куда: `.github/workflows/deploy.yml` стартера. Правка: stderr не глушить, шаги с понятными сообщениями, `SSH_KNOWN_HOSTS` как опциональный секрет, 5 повторов (как в PR #3).
29. **Запасной способ выкладки без SSH** нужен в стартере, а не придумывается в день аварии (черновик HTTPS-приёмника был заблокирован). Куда: гайд «Деплой клиента». Правка: описать официальный план Б — zip из `out/` + загрузка через файловый менеджер/FTP над TLS, с чеклистом; решение о приёмнике на PHP принимает Ник заранее.
30. **Прод без staging — осознанное решение, но правило отсутствует.** Куда: флоу этап 8. Правка: «staging можно пропустить, если у сайта нет трафика (подтверждено Метрикой) и Ник подтвердил письменно»; иначе dev-поддомен обязателен.
31. **Чеклист запуска не пройден, хотя сайт живой.** Куда: `06-launch-checklist.md`. Правка: разделить на «блокирует выкладку» (право, редиректы, формы, Метрика, базовая линия) и «после выкладки» (Вебмастер, GSC, IndexNow, Яндекс Бизнес); `check.mjs` требует отметки блокирующих пунктов перед прод-деплоем (или они автоматизируются).
